## Design Decisions (locked for this slice)

1. **One migration carries the full PRD §6.2 v0.1 schema.** `0001_initial.sql` creates all seven tables (`settings`, `prayer_times`, `iqamah_rules`, `media`, `display_groups`, `displays`, `users`) verbatim from `PRD.md:244-303`. Later slices write rows (`users` 1A-7, `media` 2A, `display_groups` 3A) instead of shipping schema migrations; only genuine shape changes need `0002_*.sql`. Rationale: §6.2 is normatively "v0.1" as a whole, `displays` is needed by this slice's heartbeat batcher anyway, and `displays.group_name`'s FK needs `display_groups` to exist — incremental migrations would split one locked schema across four PRs for zero decoupling benefit.
2. **Seeds live in the migration; identity does not.** The migration seeds non-identity settings defaults (`hijri_offset=0`, `adhan_duration_s=180`, `dim_minutes_default=20`, `dim_minutes_jumuah=45`, `boundary_countdown=0`, `method=MABIMS`), the six FR-1.4 `iqamah_rules` rows (values from `values.py:128-135`), and the `'Default'` `display_groups` row (FK target of `displays.group_name`). It does **not** seed `masjid_name`/`zone_code`/`lat`/`lon` — identity comes from the first-boot wizard (FR-6.2). `SettingsRepo.load()` on a database without those two keys raises `ConfigError("settings not initialised — run the setup wizard")`; the 1A-7 handler maps it to the wizard redirect. Optional settings keys that no `Settings` field backs yet (`carousel_enabled`, `theme_default`, `qr_visible_default`, `PRD.md:247-250`) are **not** written now — the table is already generic key/value, so their owning slices add their keys with zero migration.
3. **`DisplayRepo` port lands now, batcher with it.** The slice row names 60s heartbeat batching as this slice's deliverable, ports-first is the 1A-4 precedent, and 1A-7's HTTP handler must not reach into an adapter-internal class. `record_seen` buffers (never write-through, `PRD.md:208`); the SQLite implementation flushes one short transaction when the 60s window closes, driven by the injected `Clock.monotonic()` — no timer thread in this slice; 1A-7 calls `flush()` on shutdown.
4. **Single connection, single lock ("single writer").** `Database` owns one `sqlite3.Connection` (`row_factory=sqlite3.Row`, `check_same_thread=False`) plus one `threading.Lock`; every read/write/migration/backup goes through it. This is what makes FastAPI's `def`-handler threadpool (`PRD.md:325` single process, sync handlers) safe without async plumbing; WAL stays on for future reader concurrency.
5. **Unknown heartbeat IDs are dropped, not inserted.** Contract says IDs are pre-registered or pending-approval (`docs/api-contract.md:60`); `flush()` is an `UPDATE ... WHERE id = ?`, so unregistered IDs update nothing and are discarded (their approval flow is 1A-7/3A). Pre-registration inserts the `displays` row out-of-band.
6. **Round-trip fidelity over DB-native timestamps.** `date`/`time`/`datetime` columns store ISO-8601 text written from the value objects themselves (`fetched_at.isoformat()` preserves the tz offset; `PRD.md`'s `DEFAULT CURRENT_TIMESTAMP` never applies on our write path) — provenance (`TESTING_STRATEGY.md:43`) survives save→load byte-for-byte. `last_known` orders by ISO date text (lexicographic = chronological). `PRAGMA user_version` cannot be bound, so the runner sets it from the parsed integer filename segment.

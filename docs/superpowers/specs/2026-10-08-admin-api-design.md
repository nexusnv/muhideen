# Admin API surface — design (Option A: token-gated file-config PATCH)

Date: 2026-10-08. Status: brainstorm-approved (§§1–4), spec review fixes applied (round 4: blank-string rule, playlist-PATCH items, media atomicity, restore staging/buffer-race, manual-days date authority, preview errors, delete-reference policy, filename limits, validate merge, export-corrupt-buffer, slash-ids).
Goal: full FastAPI surface so another developer can build a frontend admin panel, without undoing the file-config decision (no DB/users/sessions).

## Context

- Current backend is read-only: `GET /api/prayer-day|next-event|events|version` + `GET /display` (`src/muhideen/api/app.py:1-7`). Config lives in `config/muhideen.json` (`ConfigFile` in `adapters/file_models.py`), cache in `prayer_buffer.json`, binaries in `media/`. `ConfigWatcher` hot-reloads + SSE `config-update`.
- `FileSettingsRepo.save` (`adapters/file_config.py:312`) already does raw-dict surgery + `ConfigFile.model_validate` + `_atomic_write_json` (`file_config.py:179`). `FilePlaylistRepo` is read-only by intent (`file_config.py:907`); displays have no repo (read inline in `display()` route).
- Historic session-auth + SQLite surface (`docs/api-contract.md:63-429`, `PRD.md:215,316-317`) was removed; `tests/test_no_admin.py:75-118` pins the removal. This design does not restore sessions/SQLite — it reintroduces admin paths (`/api/playlists`, `/api/displays`, `/api/logs`, etc.) under a different mechanism (static Bearer token over file-config, no users/sessions). That test must be updated accordingly (see §4).

## Agreed decisions

1. Auth: static API token, Bearer, file outside `muhideen.json`.
2. Scope: full `muhideen.json` CRUD (all sections + playlists/displays/manual-days).
3. Media: multipart upload API (not path-strings-only, not base64-in-JSON).
4. Update style: per-section PATCH (not single full-file PUT).

## §1 Auth + cross-cutting

- New CLI flag `--admin-token-file` (single rule, no fallback: default is always `Path(--config).parent / "admin_token"`, e.g. `--config ./config/muhideen.json` → `./config/admin_token`, `--config /etc/muhideen/muhideen.json` → `/etc/muhideen/admin_token`), argparse-only per `service.py` precedent (no env magic). The systemd unit passes `--admin-token-file /etc/muhideen/admin_token` explicitly when `--config /etc/muhideen/muhideen.json`. Token is plumbed via `create_production_app(..., admin_token_file=...)` into `AppDeps.admin_token` (in-memory string, never logged).
  - File holds one line `secrets.token_urlsafe(32)` (256-bit), mode `0600`, owned by the service user.
  - Token is read once at startup into memory; every write compares against memory with `secrets.compare_digest`. Rotation = rewrite file + restart. A post-boot change to the file has no effect until restart (documented, no per-request re-read TOCTOU).
  - Missing/empty/whitespace-only/unreadable at boot → all gated endpoints (writes + `GET /api/logs` + `GET /api/backup/export` + all `.../validate` POSTs) answer `503 {detail: "admin writes disabled"}`, public reads stay serving, boot logs a warning (no fail-fast; public display must keep serving). An empty/blank file never yields a comparable token (no empty-Bearer bypass). Auth check order is fixed: disabled-check first, then Bearer compare — a request with any token while disabled still gets `503`, never `401`.
  - `install.sh` generates once if absent (`token_urlsafe(32)`, `0600`, `chown muhideen`) and never clobbers an existing file. Token never appears in `GET /config`, logs, or error details.
  - LAN-trust assumption: the device serves plaintext HTTP on the LAN, so Bearer is sniffable on the local network. Accepted v1 (same trust as SSH/hand-edit today); document "use a trusted LAN / isolate the IoT VLAN". No TLS v1.
- Gate all writes (`PATCH/POST/PUT/DELETE` on `/api/config/*`, `/api/playlists/*`, `/api/displays/*`, `/api/media/*`, `/api/backup/restore`, including all `.../validate` dry-run POSTs) AND `GET /api/logs` AND `GET /api/backup/export` with `Authorization: Bearer <token>`.
  - Implement with `HTTPBearer(auto_error=False)` (never the default, which returns 403 on missing header). Missing/mismatched/empty → `401 {detail: "invalid admin token"}` with `WWW-Authenticate: Bearer` header. Use `secrets.compare_digest`. No sessions, no login rate-limit v1 (256-bit token is unguessable; brute-force is not the threat — LAN sniffing is, see above).
- Reads stay public (`prayer-day`, `next-event`, `events`, `version`, `display`, `GET /api/config` + section GETs, `GET /api/playlists` + `preview`, `GET /api/displays`, `GET /api/media`). `GET /api/logs` and `GET /api/backup/export` are NOT public (gated above: logs leak journald paths/errors, export bundles buffer+media). Rationale for public config: config contains no secrets (name, zones, lat/lon to 4dp, playlists/displays); masjid location is public by nature. OpenAPI gains `HTTPBearer` securityScheme; `/docs` stays public (same rationale as `app.py:654-659`). Accepted risk: public docs advertise write schemas — stated in threat model.
- Audit v1: no per-user accounts (out of scope), but every gated request (writes + gated GETs) logs at INFO `client_ip method path -> status` (timestamp via journald, endpoint, result, source IP; never the token). `client_ip` is the direct TCP peer only (`request.client.host`); `X-Forwarded-For`/`Forwarded` headers are ignored (spoofable, no proxy in front v1). Enough to correlate operator actions in `journalctl` with a shared token.
- Write semantics:
  - One shared process-wide `ConfigWriteLock` (`threading.Lock` held in `AppDeps`, passed to all writers). The existing per-instance `FileSettingsRepo._lock` / `FilePrayerRepo._lock` pattern is explicitly insufficient (separate instances do not serialize — see `file_config.py:292-297` comment) and must NOT be reused as-is. Every admin write holds the shared lock around read + merge + validate + rename. `workers=1` (`service.py:56`) makes in-process locking sufficient; cross-process writers fall back to tmp+rename last-wins (documented). Write endpoints MUST be sync `def` (like existing reads) or run lock+file-IO in a threadpool — never hold a `threading.Lock` inside `async def` (blocks the event loop for SSE/tick).
  - `_atomic_write_json` tmp+rename+fsync per `file_config.py:179` for mappings; pins-file writes need a list-capable equivalent (same tmp+rename+fsync, `json.dumps(list)` payload — current helper is typed `Mapping[str, Any]` and cannot take a bare array). Validate-before-rename: `ConfigFile.model_validate` AND `Settings` conversion (`_settings_from_config`, catches file-model gaps — see §2) AND `validate_pins` where pins are affected (pins validated against the current on-disk buffer; known races: scheduler `save_day` holds only its own `_lock`, so a buffer swap between validate and rename heals on the next watcher reload — documented, not locked; restore buffer rename vs concurrent scheduler `save_day` is accepted last-wins, next sync heals — see §4); invalid never touches disk, last-good keeps serving.
  - No optimistic concurrency v1: writes serialize on the lock with re-read-inside-lock, so concurrent PATCHes to different sections both apply (second merges over first's rename); concurrent PATCHes to the same section last-writer-wins silently. Frontend should GET-before-PATCH; document the risk rather than adding ETags v1.
  - Success publishes existing `event_bus.publish("config-update", (...))` — no new SSE channel. `ConfigWatcher._on_reload` revalidates concurrently; atomic rename guarantees it sees old-or-new, never torn.
- Errors, all JSON `{detail}` (paths scrubbed via existing `_public_detail` for `ConfigError`; Pydantic `422` echoes input values only, never server absolute paths): `401` token (+`WWW-Authenticate`), `422` validation `{detail:[{loc,msg}]}` (FastAPI/Pydantic shape, normalized even for `Settings`/`parse_window`/`parse_bound`/`ZoneInfo`/`normalize_adhan_rel` ValueErrors; malformed item fields), `404` unknown id/date/path, `409` duplicate playlist `id` / duplicate item `sort_order` (manual-days PUT is upsert, never `409`), `413` over size caps, `503` writes-disabled/broken-config, `501` logs-unavailable. No stack traces or absolute paths on the wire. Non-Pydantic `ValueError`s are mapped per-route (try/except → `422`) with `loc` convention `["body", <field>, ...]` (nested: `["body","aladhan","base_url"]`, `["body","countdown_before_adhan_overrides","fajr"]`); never leak as `500` or `{detail: string}`. The two `503`s stay distinguishable by detail text: `"admin writes disabled"` (token) vs scrubbed `_public_detail` (broken config).

## §2 Per-section config PATCH

PATCH bodies are all-optional partials; omitted = unchanged, explicit `null` clears where nullable. Free-text fields are stripped before validation and whitespace-only is rejected `422`: `masjid.name`, `schedule.zone`, `schedule.jakim.zone`, `schedule.manual_days_file`, playlist `id`/`title`, display `name` (all carry `min_length=1` in the file model, which blank strings would otherwise pass but which route/resolve as unset or render blank). Each PATCH does raw-dict surgery on its section only and preserves every other top-level section semantically (masjid, schedule, timing, theme, adhan_audio, displays, playlists, manual_days, manual_days_file) — re-serialized via `_atomic_write_json` (`indent=2`), so not byte-identical to disk (formatting normalizes; JSON has no comments to preserve). Merge depth is fixed: one-level deep merge for nested `schedule.jakim` / `schedule.aladhan` (e.g. `{aladhan:{base_url:X}}` preserves `method`); full-replace for `timing.countdown_before_adhan_overrides` (send the whole map) and `timing.iqamah_rules` (send all 6); per-knob merge for display `theme` (§3). Shallow `dict.update(patch)` at the section level without this rule would silently drop sibling keys. Then full-file `ConfigFile.model_validate` + `Settings` conversion before rename, so sibling-section invariants (e.g. provider/coords pairing) are enforced even when the PATCH touches one section. All config PATCH responses are `{ok:true, restart_required:bool}` — `restart_required=true` only for tz change (§2-masjid) and effective-sync-client change (§2-schedule); all other sections return `false`.

- `GET /api/config` (full file, export source) + `GET /api/config/{masjid,schedule,timing,theme,adhan-audio}`. `GET` returns parsed-then-reserialized JSON (not byte-identical to disk; export source for tooling, not a formatting guarantee). Full-file serialization MUST use `model_dump(by_alias=True)` so the output carries `$schemaVersion` (not `schema_version`); otherwise the export fails `POST /api/config/validate` round-trip because `ConfigFile` validates by alias only (`validate_by_name=False`).
- `PATCH /api/config/masjid`: `{name? 1-200, timezone? IANA}` → `{ok:true, restart_required:bool}` (`true` when `timezone` changed; existing `_on_reload` warns, keeps old clock). `timezone` validated via `ZoneInfo` (same as `Settings`).
- `PATCH /api/config/schedule`: `{sync_provider?, zone?, jakim:{zone?}?, aladhan:{base_url?,method?}?, method? MABIMS|MWL|ISNA|Egyptian, asr_juristic? shafi|hanafi, lat?, lon?, calc_only?, hijri_offset? -2..2, imsak_offset_min? 0-10, dhuha_offset_min? 15-30, boundary_countdown?, manual_days_file? string|null}` (`manual_days_file` is the only pins key editable here; inline `manual_days` array is never edited here — see §3). `manual_days_file` is stripped before validation: whitespace-only is rejected `422` (it would otherwise pass `min_length=1` but route as unset per `manual_days_file_for_config` blank-check).
  - `lat`+`lon` paired-or-null (`_lat_lon_paired`); `jakim.zone` (1-32 chars) required iff `sync_provider == "jakim"` after merge (`_jakim_needs_zone`); `lat`/`lon` required iff `sync_provider == "aladhan"` after merge (`_aladhan_needs_coordinates`). Switching provider without the newly-required fields in the same merged result → `422`.
  - Restart-required only for the effective sync client: changing `sync_provider`, or changing `aladhan.base_url`/`method` while effective provider is `aladhan`. Response sets `restart_required=true` in those cases (frontend shows "restart to apply sync change"). Editing `aladhan.*` while provider is `jakim` (or vice versa) hot-applies as a validated no-op (`restart_required=false`). `zone`/coords/offsets/`method`/`asr_juristic`/`calc_only`/`manual_days_file`-ref hot-reload. Inline `manual_days` excluded (see §3). Changing `manual_days_file` ref must also enforce inline+file exclusivity (`_manual_source_exclusive` → `422` if inline non-empty and ref non-null after merge).
- `PATCH /api/config/timing`: `{adhan_duration_s? >0, dim_minutes_default? 5-60, dim_minutes_jumuah? 5-60, countdown_before_adhan_min? 0-90, countdown_before_adhan_overrides? {prayer: 0-90}, iqamah_rules?[]}`.
  - `countdown_before_adhan_overrides` keys must be prayer-only (`fajr,dhuhr,asr,maghrib,isha,jumuah`); boundary keys (`imsak,syuruq,dhuha`) or unknown keys → `422`. `dhuhr` and `jumuah` are distinct keys (Friday uses `jumuah`); setting `dhuhr` does not cover Friday. File model allows any string key, so PATCH must validate via `Settings` conversion (`values.py:425-440`), not `ConfigFile` alone.
  - `iqamah_rules` when present = full 6, exactly once each (`fajr,dhuhr,asr,maghrib,isha,jumuah`); each `delay 0-60` / `fixed` requires `fixed_time: HH:MM` (`file_models.py:260-265,278-290`). Partial rule updates are not supported — send all 6.
- `PATCH /api/config/theme`: 7 enums all-optional (`palette, font, countdown_style, clock_format, hijri_form, boundary_strip, density`). `null` is invalid here (global theme is non-nullable) → `422`. Per-display `null`=inherits is only in §3.
- `PATCH /api/config/adhan-audio`: `{enabled?, volume? 0-100, quiet_hours_start/end? paired HH:MM|null, muted_prayers?[] prayer-only, file?}`.
  - `quiet_hours_*` paired-or-null (`_quiet_hours_paired`); each bound `HH:MM` when present.
  - `muted_prayers[]` prayer-only (same 6 as above; boundary/unknown → `422`). File model is `list[str]` with no validator, so enforce via `Settings` (`values.py:469-479`).
  - `volume`/`quiet_hours`/`muted_prayers` validate even when `enabled=false`; only `file` is ignored when disabled (`_file_relative_contained_when_enabled` / `resolve_adhan_path` semantics).
  - `file` is path-string only; binaries via §4. Same normalization as media (`normalize_adhan_rel`: relative, no `..` escape, no absolute, no `?`/`#`, no NUL, no trailing `/`, `media/` prefix stripped).

## §3 Resource CRUD

Shared id rules: playlist/display `{id}` path params are `1-64` chars, `[A-Za-z0-9_-]` only (no `/`, no `..`, no URL-structural chars). Unknown id/date → `404`; duplicate id on `POST /api/playlists` / duplicate `sort_order` on item POST → `409` (malformed values → `422`; see items). Exception: `PUT /api/config/manual-days/{date}` is upsert (duplicate date replaces, `200` — never `409`). Hand-edited legacy rows with out-of-grammar ids/sort_orders load and list as-is; writes enforce the grammar on new values only (legacy rows must be hand-fixed or delete+recreated via API). Legacy ids containing `/` are API-invisible (single-segment `{id}` never matches a slash at routing level — framework `404`, not JSON `404`) and must be hand-fixed; the API cannot address them.

- Playlists: `GET /api/playlists`, `POST /api/playlists` (`201` on create, duplicate `id` → `409`), `GET/PATCH/DELETE /api/playlists/{id}`; items `POST /api/playlists/{id}/items`, `DELETE /api/playlists/{id}/items/{sort_order}` (no item PATCH v1 — update duration/path via delete+POST; gaps persist, auto-assign never reuses). Register static `GET /api/playlists/preview` BEFORE `GET /api/playlists/{id}` in FastAPI (`preview` matches the id grammar, so order matters or preview 404s as unknown id).
  - `POST` requires `{id, title}` (non-empty); all other fields default as in `PlaylistFile` (`active=true`, windows/anchor `null`, offsets `0`, `cycle_mode=indefinite`, `max_cycles=null`, `items=[]`).
  - `PATCH /api/playlists/{id}` is a partial merge (omitted = unchanged, `null` clears nullable windows/anchor). Renaming `id` via PATCH is forbidden → `422` (delete + recreate instead; avoids index churn). `items` in a playlist PATCH body is forbidden → `422` (items are managed only via the items endpoints, where `sort_order` uniqueness and auto-assign apply; accepting `items` here would bypass those invariants).
  - Constraints: `0-50` image-only items (`_items_capped`); `window_start`/`window_end` = `HH:MM` clock OR any marker name (prayer or boundary, case/whitespace-tolerant per `parse_bound`) OR `null` (open); `anchor_marker` = prayer-only 6 (`fajr,dhuhr,asr,maghrib,isha,jumuah`), boundary anchors (`imsak,syuruq,dhuha`) → `422` (`parse_window`); `anchor_stop_offset_min >= anchor_start_offset_min` (equal preserves legacy always-in-window shape), else `422`; `cycle_mode=repeat` requires `max_cycles >= 1`, `indefinite` requires `max_cycles=null` (`_cycle_pairing`), else `422`. File model leaves windows/anchor unvalidated, so writes must run `_playlist_from_file` + `parse_window` before rename and normalize `422` shape.
  - Items: `{image_path (media-relative, enforced like `normalize_adhan_rel`: relative, no `..` escape after `normpath`, no absolute/drive-letter, no `?`/`#`/NUL/trailing-`/`, `media/` prefix stripped; dangling refs allowed — file may be uploaded before or after item create, existence is NOT required at item-write time), duration_s >0, sort_order >=0}`. `sort_order` unique per playlist (new API invariant; `PlaylistFile` does not enforce it): malformed (negative/missing/zero-duration) → `422`, duplicate `sort_order` on POST → `409`. Legacy files with duplicate `sort_order` list as-is (file order); `DELETE` on an ambiguous `sort_order` → `409` with hand-fix detail until deduped. `DELETE .../items/{sort_order}` addresses by `sort_order` value (stable because unique post-validation); unknown → `404`. `POST` without `sort_order` auto-assigns `max(existing)+1` (empty → `0`).
  - Preview: `GET /api/playlists/preview?moment=<tz-aware ISO>` (`moment` is required; missing → `422`) → `{stage, active_playlists[]}` via `resolve_stage` for window testing. Naive `moment` (no offset) → `422` (same `_require_tz_aware` as `next-event`). Schedule/config failures propagate with the same mapping as `prayer-day`: unresolvable date+zone → `404`, invalid config → `503`.
- Displays: `GET /api/displays`, `PUT /api/displays/{id}` (upsert), `PATCH /api/displays/{id}`, `DELETE /api/displays/{id}`.
  - `PUT` = full replace upsert: missing fields reset to defaults (`name=null`, `language="en"`, `theme={}` = all-inherit, `dim_minutes_override=null`, `carousel_enabled=true`). Returns `201` on create, `200` on replace. An empty body `{}` is valid and creates/resets to all-defaults (intended — explicit reset). `PATCH` = partial merge (omitted = unchanged, `theme.<knob>=null` = inherit that knob).
  - Body `{name? (1-200 chars or null; unbounded rejected to match `masjid.name`), language? en|ms|ar|bm, theme? partial-7 (each knob enum|null=inherits), dim_minutes_override? 5-60|null, carousel_enabled? bool}`. `language` closed literal; unknown → `422`. No schedule/iqamah fork.
- Manual-days: `GET /api/config/manual-days`, `PUT /api/config/manual-days/{date}` (`{date: YYYY-MM-DD}`), `DELETE` same.
  - `GET` returns `{source: "inline"|"file", pins: [...]}` so the client knows where writes route; `pins` is the effective array (inline `schedule.manual_days` or the pins-file bare array). If the `manual_days_file` ref is set but the pins file is absent on disk, `GET` returns `503` with a hand-fix detail (same fail-loud as `load_config_file`; the file must be created via `PUT` or the ref cleared via schedule PATCH) — it never returns an empty `pins: []` that would mask the missing file.
  - `PUT` requires ≥1 of the 8 `HH:MM` markers (`imsak,fajr,syuruq,dhuha,dhuhr,asr,maghrib,isha`; `_at_least_one_marker`), each `HH:MM` when present. Path date is authoritative: a `date` field in the body, if present, must match the path or → `422` (implementations may ignore-or-reject; mismatch never wins). Duplicate date on create uses PUT-upsert semantics (replace, `200`); structurally-invalid → `422`.
  - Source routing: if `schedule.manual_days_file` ref is set (resolved via `resolve_pins_path` / `manual_days_file_for_config`), writes go to the pins file; otherwise inline. Inline+file stays exclusive (setting both → `422`). If the ref is set but the pins file is absent, `PUT` creates it (mkdir parent, list-capable atomic write of the bare array — see §1); the ref itself can only be changed via `PATCH /api/config/schedule` (not via manual-days endpoints). Migration note: inline→file requires clearing inline first (no bulk-clear endpoint — `DELETE` each date individually, then set the ref); file→inline/null leaves the old pins file orphaned on disk (never auto-deleted; remove via SSH if desired). Orphan pins/media files are never GC'd by the API.
  - Validation is two-tier: (1) structural (markers, `HH:MM`, unique dates) always enforced; (2) buffer-completion via `validate_pins` — a partial pin with no buffer row for that date+zone fails `422` with a named detail (`"no buffer row for <date> — sync first or send a full-day pin"`). Documented trap: operators cannot pre-pin a future date before the first sync without sending all 8 markers. `DELETE` removes the date; unknown date → `404` (when the pins-file ref is set but the file is absent, `DELETE` returns `503` like `GET` — there is no file to delete from).

## §4 Media + validate + ops

- Media: `GET /api/media` (`[{path,size_bytes}]`, `path` media-relative, `size_bytes` int), `POST /api/media`, `DELETE /api/media/{path:path}`.
  - `POST` is `multipart/form-data` with fields `file` (binary, required) + `kind` (form field, `adhan|image`, required). `kind` determines destination + validation: `adhan` → media root (`<media_dir>/<basename>`), `image` → `<media_dir>/playlists/<basename>` (ensure `playlists/` subdir exists before write). Basename sanitization: take `posixpath.basename` of the client filename, strip whitespace; reject empty, NUL, `?`/`#`, trailing `/`, backslash-drive, absolute/drive-letter, `..` after `normpath`, overlong names that would fail at write (`ENAMETOOLONG` → `422`, not `500`/`503`); flatten `subdir/file.jpg` → `file.jpg` (subdirs not created v1); lower extension only for type check (stored name keeps client case). Writes use tmp-in-same-dir + rename (same atomicity as config JSON) so concurrent `/media` reads never see torn binaries — including the Pillow re-encode output. No UUID rename v1; overwrite of an existing relpath by an authenticated caller is allowed and returns `200` (new file returns `201`); response `{path}` with the normalized relpath.
  - Path rules (all kinds): media-relative only; reject `..` escape (after `posixpath.normpath`), absolute (incl. drive-letter), `?`/`#`, NUL, trailing `/`, backslash-drive; strip legacy `media/` prefix. `DELETE` uses FastAPI `{path:path}` converter, percent-decoded then normalized before the check; unknown → `404`. `DELETE` is unconditional and never validates references: removing a file referenced by a playlist item or adhan config is allowed (dangling refs stay permitted — items resolve skip-missing, adhan fails soft to silent no-audio per display behavior); no per-delete reference scan.
  - Content rules: images `jpg|jpeg|png|webp` (extension + Pillow open verified), `≤5MB` pre-encode request size (cap enforced during streaming read, before Pillow decode; re-encoded output may differ in bytes but the gate is on upload bytes), Pillow re-encode on upload (strip EXIF, enforce `Image.MAX_IMAGE_PIXELS` bomb guard, preserve format); audio `mp3` (extension + frame-sync/ID3 magic check — documented weak v1, no full decode), `≤10MB`. Oversize → `413`. Size caps are enforced by bounded streaming reads (check `Content-Length` up front when present, then read in chunks with a running total and abort at cap+1) — never buffer the full body before checking, and never rely on FastAPI/Starlette defaults (no built-in cap). Mismatched kind/ext (e.g. `kind=image` with `.mp3`) → `422`.
  - Mount fix (corrects `app.py:668` gap): always mount `/media` at startup regardless of dir existence AND `mkdir -p media_dir` at boot and after upload. `mkdir` alone is necessary but not sufficient — the mount must pre-exist so no restart is ever needed. Verify the pinned Starlette version supports `StaticFiles(check_dir=False)` before using that kwarg (older releases lack it and crash boot on unknown kwarg); if unavailable, `mkdir -p` before an unconditional `app.mount("/media", ...)` achieves the same.
- Validate (dry-run, gated like writes: Bearer required, `503` when writes-disabled; nothing written; same `422 [{loc,msg}]` shape as PATCH):
  - `POST /api/config/validate` takes a full-file `ConfigFile` candidate (entire `muhideen.json` JSON, `$schemaVersion` alias spelling required — `schema_version` snake-case is rejected per `file_models.py`) → `200 {ok:true}` or `422`.
  - `POST /api/config/{masjid,schedule,timing,theme,adhan-audio}/validate` takes the same partial body as the corresponding PATCH (merged server-side over current file for validation, using the same §2 merge-depth rule — deep-merge `jakim`/`aladhan`, replace overrides/`iqamah_rules`) → `200 {ok:true}` or `422`. Section-level validate is the primary frontend flow; full-file validate is for export/import round-trips.
  - `POST /api/config/manual-days/validate` takes a bare pins array (same shape as the pins file) → `200 {ok:true}` or `422` (structural + `validate_pins` buffer-completion, same trap message as §3).
- Ops: `GET /api/version` (exists, public); `GET /api/backup/export` (gated — see §1); `POST /api/backup/restore` (gated); `GET /api/logs?lines=200` (gated — see §1).
  - Export (zip, `≤50MB` uncompressed media cap → `413` if exceeded, summed before archiving; stream the zip response, never hold all binaries in memory): `muhideen.json` + pins file if ref set + `prayer_buffer.json` if present (byte-copied as-is, even if corrupt — backup is not validation) + `manifest.json` (`{files:[{path,size_bytes,sha256}], exported_at}`) + media binaries under `media/`. Paths in zip are always relative, never absolute.
  - Restore (multipart zip, `≤50MB` upload, same bounded-streaming enforcement as media): hardens zip-slip (reject absolute entries, `..`, symlinks, drive-letter entries), then validate-all (config via `ConfigFile`, pins via `load_manual_days_file` semantics, buffer schema via `validate_buffer`, staged pins completion-checked against the STAGED buffer via `validate_pins` semantics — not the live buffer — media relpaths via §4 rules + total-size cap) BEFORE touching disk. Apply via staging dir + ordered renames (`muhideen.json` → pins file → buffer): the staging dir MUST be on the same filesystem as the targets (e.g. `<config-dir>/.restore-*.tmp`) or renames are not atomic (`EXDEV`); remove staging on success, keep it on failure for forensics until the next restore. Media extracted additively with tmp+rename per file (overwrite same relpath, never delete unlisted files — restore is not an exact mirror; orphans persist by design); keep pre-rename backups in the staging dir, any failure rolls back renamed files from staging backup. Not single-rename atomic — documented as staged-atomic. Known window: after the first rename the watcher may reload a mixed generation (new config + old pins/buffer) and publish `config-update` if that mix validates; it converges on the next rename. Subscribers must tolerate one transient mixed-state event. Buffer race: a scheduler `save_day` landing between validate-all and the buffer rename is accepted last-wins either way (staged rename may clobber a fresh sync row; scheduler write may clobber a restored row) — next sync heals.
  - Logs: `GET /api/logs?lines=200` (`lines` int `1-1000`, default `200`, non-int/out-of-range → `422`). Runs `journalctl -u muhideen --no-pager -n <lines>` via argv (no shell), 5s timeout (timeout → `501` same as unavailable), newest-last plain text (`text/plain`). Fail-soft `501 {detail}` when journald unavailable (e.g. compose) or unit missing.
  - Frontend subscribes to existing `/api/events` (`config-update`) + 60s `next-event` poll fallback — no new realtime channel.
- Frontend ergonomics: per-endpoint `422` examples in OpenAPI; `api/fixtures/admin-*.json` + extended `tools/mock_api.py` so UI builds without a Pi. Mock runs stdlib-only on `:8001`, enforces the same `Authorization: Bearer dev-admin-token` shape on all gated endpoints (fixed token `dev-admin-token`, documented in mock README; `401`/`503` shape identical), holds state in memory (no disk), and implements fixed fixtures per path/status (`200`/`201`/`401`/`404`/`409`/`422` samples) — not full validation parity (mock returns canned `422` for known-bad fixture bodies only).
